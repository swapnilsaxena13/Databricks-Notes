# 1. Querying Files Directly in Databricks

## What does querying a file mean?

Normally, SQL queries tables. In Databricks, Spark SQL can also read
supported files directly without first creating a table.

For example:

``` sql
SELECT *
FROM json.`/path/to/customers.json`;
```

### Important syntax

The path is surrounded by **backticks** ``` ` ```

syntax.

## One file, multiple files, or a directory

``` sql
-- One file
SELECT * FROM json.`/path/export_001.json`;

-- Multiple matching files
SELECT * FROM json.`/path/export_*.json`;

-- Compatible files in a directory
SELECT * FROM json.`/path/customers-json/`;
```

When reading a directory, files should have compatible formats and
schemas.

------------------------------------------------------------------------

# 2. Self-Describing vs Non-Self-Describing Formats

## JSON and Parquet

The lecture describes JSON and Parquet as formats that work well with
direct file querying because Spark can understand or infer their
structure more easily.

``` sql
SELECT *
FROM parquet.`/path/orders/`;
```

## CSV

CSV often needs extra information:

-   Header or no header
-   Delimiter
-   Column names
-   Data types

For example:

``` text
book_id;title;author
B01;Spark Guide;John
```

Here the delimiter is `;`, not `,`.

### Interview question

**Why is CSV more difficult to query directly than Parquet?**

CSV does not reliably carry schema and parsing information. Spark may
need explicit options such as header, delimiter, and schema. Parquet
stores schema information with the data.

# 5. File Metadata

When reading multiple files, source-file information is useful for
troubleshooting.

The transcript's newer approach uses `_metadata`:

``` sql
SELECT *,
       _metadata.file_path AS source_file
FROM json.`/path/customers-json/`;
```

Useful fields mentioned in the lecture:

``` text
_metadata.file_path
_metadata.file_name
_metadata.file_size
_metadata.file_modification_time
```

### Why useful?

If one record is bad, the source-file path helps identify which input
file produced it.

### Interview point

Older examples may use `input_file_name()`. The lecture recommends
recognizing `_metadata.file_path` as the alternative in newer Databricks
environments where `input_file_name()` is no longer supported.

# 6. `read_files()`

The lecture introduces `read_files()` for querying files while supplying
reader options.

``` sql
SELECT *
FROM read_files(
  '/path/books-csv/export_*.csv',
  format => 'csv',
  header => 'true',
  delimiter => ';'
);
```

This is especially useful for CSV because parsing options can be
supplied directly.

## `_rescued_data`

The lecture states that `read_files()` attempts to infer a unified
schema. Values that do not match the expected schema can be captured in
`_rescued_data` as JSON for investigation.

------------------------------------------------------------------------

# 7. CTAS --- CREATE TABLE AS SELECT

CTAS means **Create Table As Select**.

``` sql
CREATE TABLE customers AS
SELECT *
FROM json.`/path/customers-json/`;
```

Conceptually:

``` text
Source Files → SELECT → Query Result → CTAS → Delta Table
```

CTAS derives the target schema from the query result.

### CSV with `read_files()`

``` sql
CREATE TABLE books AS
SELECT *
FROM read_files(
    '/path/books-csv/export_*.csv',
    format => 'csv',
    header => 'true',
    delimiter => ';'
);
```

This lets the CSV be parsed with required options before the CTAS result
is stored.

------------------------------------------------------------------------

# 8. `CREATE TABLE ... USING`

The lecture also creates a table that directly references CSV files:

``` sql
CREATE TABLE books_external (
    book_id STRING,
    title STRING,
    author STRING
)
USING CSV
OPTIONS (
    header = 'true',
    delimiter = ';'
)
LOCATION '/path/books-csv/';
```

### Key idea

``` text
External Table → Reference → Original CSV Files
```

No data is moved merely because this external table is registered. The
files remain CSV, so this does not automatically become a Delta table.

------------------------------------------------------------------------

# 9. External CSV Table vs Delta Table

  External CSV Table                   Delta Table
  ------------------------------------ ------------------------------
  References CSV files                 Stored in Delta format
  Source remains CSV                   Uses Delta transaction log
  Registration does not convert data   Delta capabilities apply
  Reader options describe source       Data/schema managed as Delta

**Interview statement:** Creating an external table over CSV does not
convert the CSV files to Delta.

------------------------------------------------------------------------

# 10. `REFRESH TABLE`

The lecture demonstrates new files being added to an external CSV
location while cached information prevents the additional records from
immediately appearing.

``` sql
REFRESH TABLE books_external;
```

This invalidates cached table information so Spark can re-read the
source when required.

**Interview answer:** `REFRESH TABLE` can be useful when underlying
external data changes but Spark has cached information about the source.

------------------------------------------------------------------------

# 11. Delta Lake and ACID

The lecture describes Delta Lake as supporting ACID-compliant table
updates.

-   **Atomicity:** Transaction succeeds completely or does not commit
    partially.
-   **Consistency:** Committed changes keep the table in a valid state.
-   **Isolation:** Concurrent operations are handled according to
    transactional rules.
-   **Durability:** Committed changes persist.

The lecture also discusses table versions and Time Travel.

# 12. Four Important Delta Write Operations

``` text
CREATE OR REPLACE TABLE
INSERT OVERWRITE
INSERT INTO
MERGE INTO
```

These are highly important for interviews.

------------------------------------------------------------------------

# 13. CREATE OR REPLACE TABLE

``` sql
CREATE OR REPLACE TABLE orders AS
SELECT *
FROM parquet.`/path/orders/`;
```

The lecture uses this to replace table contents and generate a new table
version.

Use it when rebuilding/replacing a table from a query is intentional and
replacing the table definition/content is acceptable.

------------------------------------------------------------------------

# 14. INSERT OVERWRITE

``` sql
INSERT OVERWRITE TABLE orders
SELECT *
FROM parquet.`/path/orders/`;
```

This replaces the existing target data using the query result.

  -----------------------------------------------------------------------
  CREATE OR REPLACE                   INSERT OVERWRITE
  ----------------------------------- -----------------------------------
  Can create or replace a table       Target table already exists

  Can replace table definition/schema Must satisfy target schema rules
  depending on operation              

  Useful for rebuilding               Useful for replacing existing data
  -----------------------------------------------------------------------

The lecture demonstrates a schema mismatch causing `INSERT OVERWRITE` to
fail.

------------------------------------------------------------------------

# 15. INSERT INTO

``` sql
INSERT INTO orders
SELECT *
FROM parquet.`/path/orders-new/`;
```

This appends records.

``` text
Existing Rows + New Rows = Final Table
```

## Duplicate risk

A simple append does not know whether the same business record was
processed previously. Re-running the same input can therefore create
duplicates.

------------------------------------------------------------------------

# 16. MERGE INTO

`MERGE INTO` can implement an **upsert**.

**Upsert = Update + Insert**

``` sql
MERGE INTO customers AS target
USING customer_updates AS source
ON target.customer_id = source.customer_id

WHEN MATCHED THEN
  UPDATE SET target.email = source.email

WHEN NOT MATCHED THEN
  INSERT (customer_id, email)
  VALUES (source.customer_id, source.email);
```

Conceptually:

``` text
Source Row
   |
Does key match target?
   / \
 YES   NO
  |     |
UPDATE INSERT
```

The command can also include delete logic when specified.

### Why useful?

-   Update existing records
-   Insert new records
-   Conditional changes
-   CDC-style processing
-   Idempotent ingestion patterns when keys and source data are designed
    correctly

### Interview caution

Do not say **"MERGE always prevents duplicates."**

Say: **MERGE can help prevent duplicate inserts when the match key and
source data are correctly designed.**

# 20. JSON String vs STRUCT

A JSON string is text. A **STRUCT** is a native Spark complex type with
named fields.

``` text
JSON STRING → from_json() → STRUCT
```

The lecture introduces:

``` text
from_json()
schema_of_json()
```

After conversion to a struct, nested fields can be accessed with dot
notation:

``` sql
profile_struct.first_name
profile_struct.address.country
```

Top-level struct fields can be expanded:

``` sql
SELECT profile_struct.*
FROM customer_profiles;
```

# 21. Arrays and EXPLODE

Suppose:

``` text
order_id = O100

books = [
  {book_id: B01, quantity: 1},
```

Using:


**Interview definition:** `EXPLODE` converts array elements into

# 22. `collect_set`, `flatten`, `array_distinct`

-   `collect_set` collects unique values during aggregation.
-   `flatten` removes one level from an array of arrays.
-   `array_distinct` removes duplicate array elements.

Example:

``` text
[[B01, B02], [B02, B03]]
          |
       flatten
          v
[B01, B02, B02, B03]
          |
    array_distinct

```

# 23. Spark SQL Joins

  Join         Meaning
  ------------ --------------------------------------
  INNER        Matching rows
  LEFT         All left rows plus right matches
  RIGHT        All right rows plus left matches
  FULL OUTER   Matched and unmatched rows from both
  LEFT SEMI    Left rows having a match
  LEFT ANTI    Left rows having no match
  CROSS        Every combination

Example:

``` sql
SELECT *
FROM order_items o
INNER JOIN books b
ON o.book_id = b.book_id;
```

# 24. Null-Safe Equality `<=>`

Ordinary equality does not make `NULL = NULL` true.

Spark provides:

``` text
<=>
```

Examples from the lecture:

``` text
5 <=> 5       → TRUE
5 <=> 7       → FALSE
NULL <=> NULL → TRUE
5 <=> NULL    → FALSE
```

Join:

``` sql
SELECT *
FROM orders o
INNER JOIN customers c
ON o.customer_id <=> c.customer_id;
```

Use it when the business logic intentionally wants two nulls to compare
as equal.

# 25. Set Operations

-   `UNION` combines results and removes duplicate rows.
-   `UNION ALL` combines results and keeps duplicates.
-   `INTERSECT` returns rows found in both datasets.
-   `EXCEPT` returns rows in the first dataset but not the second.

Useful for comparing old and new datasets.

# 26. PIVOT

Pivot turns row values into columns.

Before:

``` text
customer | year | amount
C1       | 2025 | 100
C1       | 2026 | 200
```

After:

``` text
customer | 2025 | 2026
C1       | 100  | 200
```

Example:

``` sql
SELECT *
FROM (
    SELECT customer_id, year, amount
    FROM transactions
)
PIVOT (
    SUM(amount)
    FOR year IN (2025, 2026)
);
```

Useful for reports, dashboards, and some analytical feature preparation.

# 27. Higher-Order Functions

The lecture focuses on:

``` text
FILTER
TRANSFORM
```

These work directly with complex values such as arrays.

------------------------------------------------------------------------

# 28. FILTER

``` sql
SELECT
    order_id,
    FILTER(books, b -> b.quantity >= 2) AS multiple_copies
FROM orders;
```

`b -> b.quantity >= 2` is a lambda expression.

**Meaning:** For each book `b`, keep it only when quantity is at least
2.

------------------------------------------------------------------------

# 29. TRANSFORM

``` sql
SELECT
    TRANSFORM(
        books,
        b -> b.subtotal * 0.90
    ) AS discounted_values
FROM orders;
```

This applies an expression to every array element.

### FILTER vs TRANSFORM

``` text
FILTER    → Which elements remain?
TRANSFORM → What should each element become?
```

------------------------------------------------------------------------

# 30. SQL UDF --- User Defined Function

A UDF is reusable custom function logic.

Illustrative example based on the lecture:

``` sql
CREATE OR REPLACE FUNCTION get_url(email STRING)
RETURNS STRING
RETURN CONCAT(
    'https://',
    SPLIT(email, '@')[1]
);
```

Usage:

``` sql
SELECT email, get_url(email)
FROM customers;
```

The lecture also uses `CASE WHEN` logic inside functions and mentions:

``` sql
DESCRIBE FUNCTION function_name;
DESCRIBE FUNCTION EXTENDED function_name;
```

**Interview caution:** Prefer built-in Spark functions when they already
solve the problem. Custom-function performance depends on the UDF type
and implementation.

# 40. Deduplication

## `distinct()`

``` python
df.distinct()
```

Removes duplicate complete rows.

## `dropDuplicates()`

``` python
df.dropDuplicates(["customer_id"])
```

Deduplicates based on selected columns.

### Important caution

`dropDuplicates(["customer_id"])` does not automatically mean "keep the
latest customer record." If the latest row matters, use a deterministic
ordering rule such as an update timestamp.

# 41. Handling NULL Values

## Fill

``` python
df2 = df.fillna({
    "email": "unknown@example.com"
})
```

Alternative:

``` python
df2 = df.na.fill({
    "email": "unknown@example.com"
})
```

## Drop

``` python
df2 = df.dropna()
```

or:

``` python
df2 = df.na.drop()
```

Do not blindly remove every row containing a null. Decide which fields
are required and measure how much data would be lost.

# 43. Left Anti Join

``` python
customers_without_orders = customers_df.join(
    orders_df,
    on="customer_id",
    how="left_anti"

```

Meaning:

> Return customers for whom no matching order exists.

Common use cases:

-   Customers without orders
-   Source records not yet loaded
-   Missing lookup/dimension records
-   Data-quality comparisons

# 44. Cross Join

A cross join creates every possible combination.

``` text
Customers = 100
Books = 20

Output = 100 × 20 = 2,000 rows
```

``` python
result = customers_df.crossJoin(books_df)
```

Cross joins can create extremely large outputs, so use them carefully.

# 45. What is a Shuffle?

A shuffle occurs when Spark redistributes data between
partitions/executors so related records can be processed together.

It can involve:

-   Network transfer
-   Serialization
-   Disk I/O
-   Additional processing

Joins and aggregations commonly cause shuffles.

------------------------------------------------------------------------

# 46. Broadcast Join

Suppose:

``` text
orders = very large
books  = very small
```

Spark can send the small relation to executors rather than performing a
large shuffle for both sides.

**Interview answer:** When one side of a join is sufficiently small,
broadcasting it can reduce expensive shuffle work and improve
performance.

------------------------------------------------------------------------

# 48. AQE --- Adaptive Query Execution

AQE means **Adaptive Query Execution**.

It allows Spark to use runtime statistics to adapt supported parts of
the query plan during execution.

**Interview answer:** AQE dynamically optimizes supported parts of Spark
execution using actual runtime data statistics.

Use SQL when transformations are naturally relational and the team is
SQL-focused.

# 53. Interview Questions and Model Answers

### Q1. How do you query JSON directly?

``` sql
SELECT *
FROM json.`/path/to/files/`;
```

### Q2. Why does CSV often need more configuration than Parquet?

CSV does not reliably store schema/parsing metadata. Options such as
delimiter, header, and schema may need to be supplied.

### Q3. What is CTAS?

Create Table As Select creates and populates a table from a query
result.

### Q4. Does `USING CSV LOCATION ...` convert data to Delta?

No. It registers a table over the CSV source. The files remain CSV.

### Q5. What is `read_files()`?

It is the Databricks file-reading function shown in the lecture that
accepts file-reader options directly in the query.

### Q6. `INSERT INTO` vs `INSERT OVERWRITE`?

`INSERT INTO` appends. `INSERT OVERWRITE` replaces the target's existing
data.

### Q7. Why can `INSERT INTO` create duplicates?

Re-running the same append can insert the same source records again.

### Q8. What is MERGE?

MERGE applies conditional changes between source and target data,
commonly updates for matches and inserts for non-matches.

### Q9. What is an upsert?

Update an existing match or insert a new record.

### Q10. What does EXPLODE do?

It converts array elements into separate rows.

### Q11. FILTER vs TRANSFORM?

FILTER keeps matching array elements. TRANSFORM changes each array
element.

### Q12. What does `<=>` do?

It performs null-safe equality.

### Q13. Why are DataFrames immutable?

Transformations return new DataFrames instead of modifying the existing
DataFrame in place.

### Q14. `distinct()` vs `dropDuplicates()`?

`distinct()` compares whole rows. `dropDuplicates()` can deduplicate
using selected columns.

### Q15. What is a left anti join?

It returns left-side rows that have no match in the right-side dataset.

### Q16. What is a broadcast join?

It sends a small relation to executors to reduce certain expensive
shuffle operations in a large join.

### Q17. What is AQE?

Adaptive Query Execution adjusts supported execution decisions using
runtime statistics.

### Q18. How do you save a DataFrame as a table?

``` python
df.write.saveAsTable("table_name")
```

# 54. Common Interview Traps

1.  **CSV external table = Delta table** → Wrong. Registering CSV does
    not convert it to Delta.
2.  **INSERT INTO prevents duplicates** → Wrong. Repeated appends can
    duplicate records.
3.  **MERGE always prevents duplicates** → Wrong. Correct keys and
    source preparation are required.
4.  **JSON-looking value must be STRUCT** → Wrong. It can still be a
    STRING.
5.  **EXPLODE creates columns** → Wrong. It normally creates rows from
    array elements.
6.  **DataFrame transformations modify the original DataFrame** → Wrong.
    DataFrames are immutable.
7.  **dropDuplicates(\["id"\]) always keeps the newest row** → Wrong. No
    "newest" rule exists unless you define one.
8.  **Broadcast every small-looking table** → Wrong. Actual size,
    resources, plan, and runtime matter.
9.  **Cross joins are cheap** → Wrong. Output grows as
    `left_rows × right_rows`.

# 57. Final Interview Takeaway

For every command, learn five things:

**What does it do? → Why do we need it? → When should we use it? → What
is the alternative? → What can go wrong?**

That is much stronger in an interview than memorizing syntax alone.
