# 1. Lakeflow Declarative Pipipelines --- Basic Idea

Lakeflow Declarative Pipelines (LDP) is presented in the transcript as
an ETL framework for building reliable and maintainable data pipelines.

It is based on Apache Spark, but uses a **declarative approach**.

## Declarative means

Instead of telling the system every execution step, you mainly describe:

> **What result/table you want.**

The framework handles more of the execution details.

Simple mental model:

``` text
Normal imperative thinking:
Read data
→ configure stream
→ transform
→ configure checkpoint
→ configure writer
→ write target

Declarative pipeline:
Define source + desired transformation + target object
→ framework manages much of the execution
```

The transcript says the framework automatically helps with:

-   dependencies between tables,
-   orchestration/order of execution,
-   checkpoints,
-   retries,
-   performance optimization,
-   CDC processing,
-   SCD Type 2,
-   data-quality controls.

## Naming to recognize in interviews

The transcript contains multiple names because the product terminology
has evolved:

``` text
Delta Live Tables (DLT)
        ↓
Lakeflow Declarative Pipelines (LDP)
        ↓
Spark Declarative Pipelines (SDP)
```

The important interview point is to recognize that older material and
existing projects may still use **DLT** terminology.

# 2. Why Use a Declarative Pipeline?

Suppose your pipeline has:

``` text
Raw Orders
    ↓
Clean Orders
    ↓
Daily Sales
```

The second table depends on the first, and the third depends on the
second.

In a declarative pipeline, the system can understand these dependencies
from your definitions and construct a DAG.

## DAG

**DAG = Directed Acyclic Graph**

Conceptually:

``` text
orders_raw
     ↓
orders_cleaned
     ↓
daily_customer_books
```

The DAG shows:

-   pipeline objects,
-   dependencies,
-   processing flow/order.

### Interview answer

**Q: What is the main benefit of Lakeflow Declarative Pipelines?**

**Answer:** It lets us define the desired datasets and transformations
declaratively while the framework manages orchestration, dependencies,
checkpoints, retries, and other pipeline execution details.

# 3. Spark Structured Streaming vs Declarative Pipelines

The transcript compares standard Spark streaming with LDP/SDP.

## Spark Structured Streaming

Typical PySpark pattern:

``` python
df = spark.readStream...

query = (
    df.writeStream
      .option("checkpointLocation", checkpoint_path)
      .toTable("target")
)
```

You explicitly deal with streaming reads and writes.

## Declarative pipeline

In Python, a table decorator is used.

Conceptually:

``` python
@dp.table
def orders_raw():
    return streaming_dataframe
```

The transcript's key point is:

> You do not explicitly call `writeStream` for the declared table.

The table declaration/decorator is responsible for the target object and
the framework manages checkpointing.

## SQL difference

The transcript says standard Structured Streaming cannot create the
complete streaming pipeline using SQL alone in the same way; PySpark is
needed to establish streaming DataFrames.

The declarative pipeline framework supports SQL-native streaming-table
declarations, such as:

``` sql
CREATE OR REFRESH STREAMING TABLE ...
```

### Interview comparison

  -----------------------------------------------------------------------
  Spark Structured Streaming          Declarative Pipelines
  ----------------------------------- -----------------------------------
  More execution details handled      More execution details abstracted
  manually                            

  `readStream` / `writeStream`        Declare pipeline objects

  Checkpoint configuration is         Framework manages checkpointing
  explicit                            

  Dependency orchestration is more    Dependencies are automatically
  manual                              derived

  Streaming setup commonly uses       Streaming tables can be declared in
  PySpark API                         SQL

  Lower-level control                 Higher-level ETL abstraction
  -----------------------------------------------------------------------

# 4. Main Pipeline Object Types

The transcript introduces three major object types:

1.  **Streaming Table**
2.  **Materialized View**
3.  **Temporary View**

Understanding when to use each is a major interview topic.

------------------------------------------------------------------------

# 5. Streaming Table

A streaming table is a **permanent object** persisted to the data
catalog.

It is designed for **incremental processing**.

Conceptually:

``` text
Run 1:
Process files 1, 2, 3

Run 2:
Process only new file 4

Run 3:
Process only new files 5, 6
```

The transcript associates streaming tables with append-only streaming
sources such as:

-   Kafka,
-   Auto Loader,
-   append-only tables read as streams.

## SQL idea

``` sql
CREATE OR REFRESH STREAMING TABLE orders_raw
AS
SELECT *
FROM STREAM(...);
```

The exact source syntax depends on the source.

## Python idea

A function returning a streaming DataFrame is decorated as a table.

### Best use cases

Use a streaming table when:

-   data continuously arrives,
-   source is streamable,
-   source follows the append-oriented requirements described in the
    transcript,
-   incremental/near-real-time ingestion is required.

### Interview phrase

> **Streaming table = permanent incremental dataset.**

------------------------------------------------------------------------

# 6. Materialized View

A materialized view is also a **permanent object** persisted to the data
catalog.

The transcript describes materialized views as useful for:

-   batch/full-refresh processing,
-   complex joins,
-   complex aggregations,
-   BI/dashboard acceleration,
-   non-streamable sources,
-   sources containing updates, deletes, or overwrites.

Example:

``` text
customers source
can be updated/deleted/overwritten
        ↓
Materialized View
```

Why not a streaming table in that example?

Because the transcript's streaming model expects append-only/streamable
input, while customer source data can be changed or overwritten.

The transcript also notes that serverless compute may optimize some
materialized-view queries to refresh incrementally.

### Interview phrase

> **Materialized view = persisted precomputed result, useful for
> batch/non-streamable sources and expensive aggregations or joins.**

------------------------------------------------------------------------

# 7. Temporary View

A temporary view is scoped to the pipeline.

It is **not persisted to the data catalog**.

Use it for:

-   intermediate transformations,
-   temporary processing,
-   data-quality logic,
-   helper datasets that do not need to become permanent tables.

### Interview phrase

> **Temporary view = intermediate pipeline-only object.**

# 9. Data Quality with Expectations

Declarative pipelines support **expectations**.

An expectation is a rule that data should satisfy while flowing through
the pipeline.

Example rule:

``` text
quantity > 0
```

This means:

> Every order is expected to have a positive quantity.

The transcript describes three main behaviors:

1.  Warn / keep invalid rows
2.  Drop invalid rows
3.  Fail the flow

------------------------------------------------------------------------

# 10. Expectation --- Warning Behavior

If no special violation action is configured, the transcript says the
invalid row remains in the target table, but the violation is recorded
in metrics.

Conceptually:

``` text
quantity = -2
     ↓
Expectation fails
     ↓
Row still written
     ↓
Violation count recorded
```

Use this when the condition is important to monitor but should not stop
processing.

------------------------------------------------------------------------

# 11. Expectation --- Drop Invalid Records

The transcript demonstrates an `ON VIOLATION` action that drops invalid
records.

Conceptually:

``` text
quantity = -2
     ↓
Expectation fails
     ↓
Row removed
     ↓
Violation recorded in metrics
```

Python equivalent described in the transcript:

``` text
expect_or_drop
```

Use this when invalid data should not reach the target but should not
stop the entire pipeline.

------------------------------------------------------------------------

# 12. Expectation --- Fail the Flow

A strict expectation can cause the flow to fail.

Conceptually:

``` text
Critical rule fails
      ↓
Flow fails
      ↓
Transaction rolled back
      ↓
Issue must be corrected
```

Python equivalent described:

``` text
expect_or_fail
```

Use this for critical business/data-integrity requirements.

------------------------------------------------------------------------

# 13. Expectation Functions to Remember

The transcript lists:

``` text
expect
expect_or_drop
expect_or_fail
```

For multiple expectations in Python:

``` text
expect_all
expect_all_or_drop
expect_all_or_fail
```

### Interview comparison

  Behavior           Result
  ------------------ ------------------------------------
  Expect / warning   Keep invalid row + record metric
  Drop               Remove invalid row + record metric
  Fail               Fail flow and roll back update

# 15. Bronze Layer in the Transcript

The Bronze layer contains two objects:

``` text
orders_raw
customers
```

## `orders_raw`

Orders arrive as JSON data and are ingested incrementally with Auto
Loader.

The transcript uses SQL `read_files` together with streaming syntax to
enable Auto Loader-style ingestion.

Conceptually:

``` sql
CREATE OR REFRESH STREAMING TABLE orders_raw
AS
SELECT *
FROM STREAM(
  read_files(...)
);
```

The transcript configures:

-   source location,
-   JSON format,
-   `inferColumnTypes = true`.

Because the read is streaming, the target is declared as a **streaming
table**.

## `customers`

Customer JSON data is treated differently.

The source may be:

-   updated,
-   deleted,
-   overwritten.

Therefore it does not satisfy the append-only streaming requirement
described in the transcript.

So customers is created as a:

``` text
Materialized View
```

and read in batch mode.

### Interview lesson

Object type should be selected based on **source behavior**, not just
personal preference.

# 17. Silver Layer

The Silver table is:

``` text
orders_cleaned
```

It:

-   reads `orders_raw` as a stream,
-   joins/enriches orders with customer information,
-   applies data-quality expectations.

The transcript uses three quality rules.

## Rule 1 --- Positive quantity

``` text
quantity > 0
```

Violation action:

``` text
DROP
```

Invalid rows do not enter the target.

## Rule 2 --- Valid customer

Customer first and last names must be available.

Violation action:

``` text
FAIL
```

A violation fails the pipeline flow.

## Rule 3 --- Recent order

Order timestamp should be newer than a specified date.

No special violation action is defined.

Therefore:

``` text
Invalid row stays
+
Violation appears in metrics
```

This behaves like a warning.

# 30. Task Dependencies

The second task runs after the first task succeeds.

The third task runs after the pipeline task succeeds.

Conceptually:

``` text

   ↓ success

   ↓ success

```

This creates workflow orchestration.

### Interview answer

**Q: What is a multi-task Databricks Job?**

**Answer:** It is a job containing multiple tasks with dependencies.
Databricks orchestrates the tasks according to those dependencies,
allowing notebooks, pipelines, and other workload types to form one
workflow.

# 43. Bundle Variables

Variables make configurations reusable.

Instead of hardcoding:

``` text

```

everywhere, define a variable.

Conceptually:

``` yaml

  catalog_name:
    default: main_catalog
```

Then reference the variable in resource definitions.

The transcript also shows environment-specific overrides:

``` yaml

  dev:
    variables:
      catalog_name: dev_catalog

  prod:
    variables:
      catalog_name: prod_catalog
```

So:

``` text
Deploy -t dev  → dev_catalog
Deploy -t prod → prod_catalog
```

# 44. CLI Variable Override

The transcript also shows deployment-time override:


The transcript states that command-line deployment variables have higher
precedence than defaults and target-specific values.

For that deployment:

``` text

```

### Important transcript point

Variable substitution happens at **deployment time**.

Therefore the transcript says passing the same style of variable to
`bundle run` does not change a value that was already resolved and
deployed.

# 56. Very Important Interview Comparison --- Streaming Table vs Materialized View

**Question:** When would you use a streaming table versus a materialized
view?

**Answer:**

Use a **streaming table** when data is incrementally arriving from a
streamable append-oriented source and you want
incremental/near-real-time processing.

Use a **materialized view** when you want to persist a precomputed
result such as a complex aggregation/join or when the source is not
suitable for append-only streaming because it may contain updates,
deletes, or overwrites.

# 60. Interview Questions and Short Answers

## Q1. What is Lakeflow Declarative Pipelines?

A declarative ETL framework based on Spark where we define desired
datasets/transformations and the framework manages much of the
orchestration and execution complexity.

## Q2. What was it previously called?

The transcript identifies the older name as **Delta Live Tables (DLT)**
and also discusses newer Spark Declarative Pipelines terminology.

## Q3. What are the three object types discussed?

Streaming tables, materialized views, and temporary views.

## Q4. Is a streaming table persisted?

Yes, the transcript describes it as a permanent catalog object.

## Q5. Is a temporary view persisted?

No. It is scoped to the pipeline.

## Q6. What source is appropriate for a streaming table?

A streamable append-oriented source such as Auto Loader/Kafka or an
append-only table read as a stream.

## Q7. Why use a materialized view?

For precomputed aggregations/joins, batch sources, or sources containing
changes that do not fit append-only streaming.

## Q8. What are expectations?

Data-quality constraints applied while data flows through the pipeline.

## Q9. What happens by default when an expectation fails?

The transcript says the invalid row remains, while the violation is
recorded in metrics.

## Q10. What does `expect_or_drop` do?

Drops records that violate the condition and tracks the violation.

## Q11. What does `expect_or_fail` do?

Fails the corresponding flow and rolls back the update when a violation
occurs.

## Q12. What is a dry run?

A validation run that checks definitions without persisting the final
pipeline tables.

## Q13. Can SQL and Python be mixed in one pipeline?

Yes, according to the transcript.

## Q14. Triggered vs continuous pipeline?

Triggered processes currently available data and stops. Continuous
remains running to process incoming data.

## Q15. What is a multi-task job?

A Databricks Job containing multiple tasks with dependencies.

## Q16. What is Repair Run?

A feature for rerunning failed job tasks after correcting the issue
without rerunning all successful work.

## Q17. What are DABs?

A deployment-as-code mechanism for defining and deploying Databricks
jobs/pipelines across environments.

## Q18. Main bundle commands?

`bundle init`, `bundle validate`, `bundle deploy`, and `bundle run`.

## Q19. What is `databricks.yml`?

The main YAML configuration file for a bundle project.

## Q20. What are bundle targets?

Environment-specific deployment configurations such as dev and prod.

## Q21. Why use bundle variables?

To avoid hardcoding environment-specific values and make configurations
reusable.

## Q22. What does `--auto-approve` do?

Skips interactive deployment confirmation, which is useful for CI/CD.

## Q23. What does `--fail-on-active-runs` do?

Stops deployment if relevant jobs/pipelines currently have active runs.

## Q24. What is `bundle generate`?

It generates bundle configuration for an existing workspace resource.

## Q25. What is Databricks Connect?

It allows local development while executing code interactively on remote
Databricks compute.

> Lakeflow Declarative Pipelines, previously known as Delta Live Tables

> Spark. Instead of manually managing every streaming write, checkpoint,

> transformations, and the framework manages much of the execution and
> orchestration. For example, I can build a Medallion pipeline where
> incoming orders are loaded incrementally into a Bronze streaming table

> define expectations such as dropping rows with invalid quantities or
> failing the flow for critical customer-data issues. The pipeline
> automatically shows dependencies as a DAG and exposes data-quality
> metrics. For production orchestration, I can run the pipeline as part
> of a Databricks multi-task Job, and for CI/CD I can define the job and
> pipeline in a Declarative Automation Bundle and deploy the same
> project to dev and prod using environment-specific targets and
> variables.
